# 01 · 设计宪法（L0 约束层）

继承 PokeWalk 的方法论：**约束先于策划落笔**。所有系统设计（docs/systems/Sxx）
不得违背本文件；修宪需在 reports/ 留档理由。

## 1. 硬约束清单

| 约束 | 内容 | 对设计的直接影响 |
|---|---|---|
| **双端目标** | 同一份 C 内核（逻辑+页面+渲染）编译为 **ESP32-C3 固件** 与 **Web 同源预览** 两条产物 | 浏览器不得自行计算布局/字体/动画——只解码内核吐出的帧（继承 PokeWalk 固件同源预览，见 §2.5） |
| **屏幕** | 240×320 RGB565，SPI 受限，**无整帧缓冲**（实测可用堆 ~231KB） | 条带渲染 + 局部重绘；棋盘 ≤7 列（32px 格 × 7 = 224px）；单位体积按 32px 级小图设计 |
| **输入** | **ABC 三键**，BSP 提供六事件：PRESS / RELEASE / CLICK / DOUBLE / LONG / END | 一切页面必须光标化/线性化；PokeWalk 裁定：A=上、B=下（长按 600ms 返回）、C=确认（长按熄屏）。自走棋优势：战斗阶段零输入，操作全在准备阶段 |
| **算力内存** | 单核 RISC-V 160MHz，无 PSRAM | 解算器 C 移植约束：定长状态、免动态分配、慎用浮点（倾向定点）；Python `sim/` 是 C 内核的**参考实现**，写法需可移植（PokeWalk sensing.py 先例） |
| **模式** | 设备无实时对战网络 → 单机：玩家 vs 7 名机器人训练家打满整轮 | 机器人经济/摆位 AI 是**发布件**而非平衡工具；多人对战不在范围内 |
| **数据边界** | 宝可梦数据只来自 PokeWalk 固定提交的 pokecrystal 提取链 + 手工属性表 | 不手抄百科数值；`data/` 是生成物，可重建可审计 |
| **同人边界** | 原作素材来源逐项声明，不声称为本项目原创 | 继承 PokeWalk 的来源声明实践 |
| **sim 依赖** | `sim/` 只用系统 python3 标准库 | 平衡验证在任何机器秒级可跑，不装环境 |

## 2. 方法论条款

1. **sim-first**：任何数值/规则改动，先在 `sim/` 里跑出几百局的影响再进实现。
   「调一次参数在表现层要重做一局，在 sim 里是几秒钟」。
2. **确定性**：战斗解算的所有随机来自显式传入的 RNG；同种子必须产生同一条
   **事件流**（`sim/prototype.py` 的确定性自检常驻）。
3. **数据派生优先**：棋子面板、攻速、射程、招式尽量从种族值/学习表推导，
   手写数值必须注明理由（例：`LEVEL_BY_TIER` 是占位设计）。
4. **文档驱动**：系统定稿进 `docs/systems/Sxx-*.md`（一系统一文件、可独立验收），
   过程验证进 `reports/`（按日期命名）。
5. **同源渲染验收**：Web 预览与设备渲染一致性以像素级对账为准
   （PokeWalk 做法：native 进程与浏览器 Canvas 的 RGBA SHA-256 逐帧一致），
   不以「看起来一样」为准；构建按源文件 SHA-256 键控，预览不读写真机存档。
6. **渲染同步契约**：解算器输出离散**事件流**，渲染端（Web/设备）只是回放器。
   同种子 → 同事件流 → 同画面。事件流的任何字段变更视同接口变更，需同步更新两端。
7. **玩法原型先于平衡**：新机制先用最小实现跑通，数值收敛放在有博弈模拟
   （机器人买入 AI）之后——随机阵容的平衡报告只能看方向，不能当结论。

## 3. 已裁定的玩法红线

- 不做一击必杀、不做 PP（能量制替代）、不做 GPS/现实感知类玩法（那是 PokeWalk 的事）；
- 属性克制表按金银世代 17 系（含恶/钢），不引入后世妖精系；
- 宝可梦池限关都 151 + 其金银血缘（宝宝形态仅作族内深度，不单独入池）；
- 不做多玩家联网对战；设备端为单机锦标赛（vs 7 bot）。

## 4. 目录契约

```
sim/      玩法仿真（纯逻辑，无 IO 依赖除 data/）——同时是 C 内核的参考实现
data/     生成物：pokemon / typechart / moves 三表（tools/ 可重建）
tools/    数据提取与管线（后续：双端构建、预览服务）
docs/     00 头脑风暴 → 01 宪法（本文件）→ systems/Sxx 定稿系统
reports/  按日期命名的验证与决策报告
```

`firmware/`（ESP-IDF 工程）与 Web 预览服务在 M4 双端架构落地时加入，
届时 sim 中定稿的逻辑按「参考实现 → C 移植 + 事件流对账」流程迁移。
