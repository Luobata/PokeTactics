# 02 · 美术与页面布局设计（240×320 专项）

状态：**草案**。本文回答两个问题：小屏幕上自走棋长什么样、
现有 PokeWalk 美术资产能直接吃下多少。

## 1. 美术方向

**金银世代像素风，原样继承 PokeWalk 的资产体系**：
每只精灵 4 色独立调色板（RGB565）、2bpp 位图、无抗锯齿整数缩放。
自走棋棋子多而小，风格统一比单只精细更重要——所有棋子同档尺寸、
同底座语言，靠**底座色彩**而不是精灵本体差异表达羁绊信息。

### 1.1 信息用色彩编码（棋子底座语言）

小屏幕上玩家要一眼读出三层信息，全部压进底座：

| 信息层 | 美术语言 |
|---|---|
| 属性/羁绊 | 底座色环：单属性一圈色环，双属性双环（外主内副）；17 系固定色相表 |
| 费用档 | 环色饱和度/亮度分档，或底座外沿描边（1费灰/2费绿/3费蓝/4费紫/5费金） |
| 进化阶段 | 底座形状：1 阶圆座 / 2 阶圆角方 / 3 阶菱形；角标星点辅助 |

属性色相表（17 系，RGB565 定稿时校色）：
火=红、水=蓝、草=绿、电=黄、冰=浅青、格斗=橙棕、毒=紫、地面=土黄、
飞行=天灰、超=粉紫、虫=草绿、岩=褐、鬼=深紫、龙=宝蓝、恶=暗灰、钢=银灰、普=米白。

### 1.2 资产复用清单（PokeWalk 现成，含实测字节数）

| 资产 | 规格 | 体积 | 用途 |
|---|---|---|---|
| gen1/gen2_front.bin | 151 张，40/48/56 三档 2bpp | 2×88 KB | 棋子（若选 40px 格方案）/图鉴 |
| gen1/gen2_back.bin | 151 张 @48×48 | 2×85 KB | 图鉴/详情页 |
| palettes(+2).bin | 每只 4 色+闪光套，RGB565 | 2.5+2.3 KB | 棋子着色原样可用 |

### 1.3 动效预算（观战乐趣的主要来源）

| 时机 | 动效 | 成本 |
|---|---|---|
| 待机 | 呼吸（±1px 缩放，effects.py 先例） | 0 |
| 普攻命中 | 受击闪白 1 帧 + 攻击者 2px 前顶 | 0 |
| 大招 | 名称条（font16）+ battle_fx 按属性映射 + 抖动 | 复用 |
| 克制 | 「效果拔群」文字弹出（金银文案） | 0 |
| 死亡 | 闪白 2 帧 → 缩小消失 | 0 |
| 进化 | 光球八轮切换压缩到 2.5s（PokeWalk 8.5s 太长） | 复用 |
| 三合一合成 | 两只飞入 + 白闪 | 0 |

### 1.4 缺口资产清单（需要新做的）

1. **32px 级棋子图**（仅当布局选 32px 格方案）：GSC 菜单图标提取管线
   （pokecrystal `gfx/icons/`，251 只全有，尺寸待核对）或 40 档缩采样逐只验收；
2. **8px 数字小字库**（伤害数字/金币）：16px 的 font16 在棋盘上太大；
3. 棋盘格 tile（双色调草地/沙地，8×8 平铺）+ 中线；
4. 金币/爱心/等级图标 8×8 各一枚；
5. 羁绊面板的 17 系图标（v1 可用色块+汉字缩写顶替）。

## 2. 页面布局：三个方案（核心取舍：格子大小 vs 摆位纵深）

40px 是精灵原生档位（40/48/56 中最小），240px 宽放 6 列正好；
放 7 列格子就只有 32px，精灵必须缩图。由此三个方案：

### 方案 A · 全景 32px（7×6 棋盘，摆位深度优先）

```
┌────────────────────────┐
│ ♥20 ⓖ15 Lv5  R12  [羁] │  顶HUD 28px
│ ┌──┬──┬──┬──┬──┬──┬──┐ │
│ │     敌方 3×7        │ │
│ │     己方 3×7        │ │  棋盘 224×192（32px 格）
│ └──┴──┴──┴──┴──┴──┴──┘ │
│ 备战 ▢▢▢▢▢▢▢▢          │  备战 36px
│ [妙蛙种子1][皮卡丘2][…] │  商店 52px
│ [刷新2] [经验4]         │
└────────────────────────┘  28+192+36+52=308+边距=320 ✓
```
- ✅ 每方 21 格，摆位纵深最好；sim 现行 7×6 直接对应
- ✗ 棋子要 32px 缩图（缺口资产①）；[羁] 羁绊入口挤成图标

### 方案 B · 大格 40px（6×4 棋盘，精灵质量优先）

```
┌────────────────────────┐
│ ♥20 ⓖ15 Lv5  R12       │  顶HUD 28px
│ ┌────┬────┬────┬────┬─ │
│ │    敌方 2×6         │ │
│ │    己方 2×6         │ │  棋盘 240×160（40px 格）
│ └────┴────┴────┴────┴─ │
│ 羁绊速览：水④ 电② …    │  羁绊条 36px（常驻！）
│ 备战 ▢▢▢▢▢▢           │  备战 36px
│ [妙蛙种子1][皮卡丘2][…] │  商店 48px
└────────────────────────┘  28+160+36+36+48=308 ✓
```
- ✅ 40px 档精灵原生直用（48/56 档只缩一档，多数可接受）
- ✅ 富余出**常驻羁绊速览条**（自走棋最常看的信息）
- ✗ 每方 12 格摆位浅；己方仅 2 行

### 方案 C · 备战行并入棋盘（6×6 棋盘，设备化改造）★倾向

```
┌────────────────────────┐
│ ♥20 ⓖ15 Lv5  R12       │  顶HUD 28px
│ ┌────┬────┬────┬────┬─ │
│ │    敌方 3×6         │ │
│ │    己方上场 2×6     │ │  棋盘 240×240（40px 格）
│ │▒   备战行 1×6 ▒     │ │  （末行虚线格=不上场）
│ └────┴────┴────┴────┴─ │
│ [妙蛙种子1][皮卡丘2][…]│  商店 48px
│ [刷新2][经验4]          │
└────────────────────────┘  28+240+48=316 ✓
```
- ✅ 40px 精灵 + 敌方 3 行纵深都保住；备战席零额外空间
- ✅ 「备战行」是清晰的设备化表达：虚线格=观战席，拖出线外才上场
- ✗ 上场格 12（人口 9 仍够）；概念上多一条教学文案
- ✗ 羁绊速览进二级页（顶 HUD 角标显示已激活数）

**建议先做 C 的静态线框真机预览再定**（成本一张图），sim 侧改 `COLS=7→6`
是一行常量，随布局定稿同步。

## 3. 其余页面（信息分级：常驻 / 一键 / 二级）

| 页面 | 内容 | 进入 |
|---|---|---|
| 战斗页 | 棋盘全屏 + 双方 HP 条 + 倍速角标 | 准备确认后自动 |
| 羁绊页 | 17 系列表、激活状态、下一档差几只 | 顶 HUD [羁] |
| 棋子详情 | 大图（48 原生）+ 种族值 + 招式 + 合成进度（2/3） | 棋盘光标 C 长按 |
| 图鉴/战绩 | 淘汰顺序、各家阵容 | 菜单二级 |
| 商店详情 | 焦点格棋子的迷你属性卡 | 商店光标停留 |

小屏原则：**主页面只放「每 10 秒看一次」的信息**（HP/金/等级/轮次/羁绊计数），
「每 2 分钟看一次」的全进二级页（图鉴、战绩、详情）。

## 4. 战斗呈现：2D 定稿与观战画面（2026-09-13 补充）

### 4.1 2D 还是 3D —— 全 2D 像素，无例外

| 维度 | 结论 |
|---|---|
| 设备可行性 | ESP32-C3 无 GPU 无 FPU、231KB 堆、条带渲染——软件 3D 光栅化在 240×320 上既跑不动也没意义 |
| 同源宪法 | 浏览器不得自行计算画面（宪法 2.5），Web 高配 3D = 两套表现层 + 双倍美术/动画成本，直接违反 |
| 资产复用 | PokeWalk 全套提取资产是 2D 四色像素（精灵/特效/字库/调色板），3D 意味着从零重做 |
| 作品身份 | 「金银世代像素」就是本作的身份；分辨率越克制越像它 |

**定稿：双端全 2D。表现力投资走「juice」而非维度**——调色板动画、震屏、顿帧、
粒子（受限调色板内）这些 2D 域内的手法，成本全部进现有资产预算。

### 4.2 战斗画面结构：俯视棋盘全景 + 大招特写切镜

战斗阶段替换全部准备期 UI，只留：全屏棋盘 + 双方 HP 条 + 倍速角标。

1. **主视角 = 俯视全景，无镜头运动**：所有单位同时可见——「3 秒读懂战况」
   是观战可读性的宪法级要求（docs/03 §2），镜头跟随/缩放在 240×320 上等于自残；
2. **精灵朝向**：正面图双方共用，一侧水平镜像（零成本，gen 正面图天然适合）；
3. **大招特写切镜（本节核心设计）**：`cast` 事件触发 → 全屏短暂切入经典对战构图
   （施法者正面大图 56px ×2 整数放大 = 112px + 招式名横幅 + battle_fx 属性特效）
   → 0.8~1.2s 回到棋盘。多个大招按事件流顺序串行排队。
   - 「宝可梦时刻」（经典侧视对战构图、效果拔群弹字）与自走棋的全局可读**兼得**：
     平时看棋盘，大招看脸；
   - 设备可行：112×112 2bpp + 调色板 ≈ 12.5KB，条带渲染下整屏重绘一张大图
     约 8 个横带，60ms 帧时钟内可完成（PokeWalk 对战页先例）；
   - 事件流天然支持：`cast` 事件已带招式名/克制倍率/伤害，渲染端零额外逻辑；
4. **观战节奏**：默认 2x（sim 时长中位 7.8s → 观感 ~4s），A/B 切 1x/2x/4x/跳过，
   长按 C 熄屏；跳过直接显示结算横幅；
5. **动画时钟**：渲染端按事件流时间戳驱动 60ms 步进时钟（PokeWalk 动画时钟先例），
   预览页支持暂停/单步——同种子逐帧对账就靠它。

### 4.3 动效手法清单（全部 2D 域内，标注成本）

| 手法 | 用途 | 成本 |
|---|---|---|
| 调色板循环 | 水面微光、电光闪烁、羁绊光环呼吸 | 0（GBC 经典技法） |
| 四件套（呼吸/闪白/缩放/抖动） | 待机/受击/死亡/选中 | 0（effects.py 先例） |
| 震屏（滚动偏移 1-2px） | 大命中/大招落地 | 0 |
| 顿帧（hit-stop 1 帧） | 普攻命中反馈 | 0 |
| 伤害数字 8px 三色 | 白=普攻/黄=大招/红=克制加成 | 小字库（缺口资产②） |
| 「效果拔群/效果不佳」弹字 | 克制反馈、知识奖励 | 0（font16） |
| 大招特写切镜 | 见 4.2.3 | 复用正面图+battle_fx |
| 进化光球八轮压缩版 | 三合一进化演出 2.5s | 复用 |
| 死亡：闪白→缩小消失 | 阵亡反馈 | 0 |

Web 端像素 1:1 入 Canvas、整数倍放大（2x/3x）；扫描线等滤镜只做 CSS 叠层、
不进画布（PokeWalk 80px 辅助线先例：叠层不污染像素对账）。

### 4.4 被否决的呈现方案

| 方案 | 否决理由 |
|---|---|
| 全程侧视经典对战构图 | 丢失 12+ 单位同时行动的空间信息；自走棋的核心体验是「看全局战局」 |
| Web 独立 3D 高配模式 | 违反同源渲染宪法；美术与维护成本翻倍；两端体验分裂 |
| 镜头跟随/智能聚焦 | 小屏全局可读性优先；镜头运动会掩盖事件流的全局语义 |
| 骨骼/补间动画 | 显示带宽宪法排除；逐帧像素+程序动效的表现力足够（GBC 名作已证明） |

### 4.6 招式动画节拍表（抬手/特效/判定/后摇，2026-09-13 定稿）

回答「技能是否有抬手动画和技能特效」：**有，且是双层的**——普攻有小抬手，
大招有完整四段节拍。渲染端由事件流 + 60ms 动画时钟驱动，无额外逻辑。

**普攻节拍**（总长 = 攻击间隔 0.63~1.36s，按速度伸缩）：

| 相位 | 时长占比 | 表现 |
|---|---|---|
| 抬手 | 0-15% | 后仰 1px（近战蓄力感）/ 后拉（远程拉弓感） |
| 命中帧 | 15% | 前顶 2px + 目标闪白 1 帧 + **顿帧 60ms**（hit-stop）+ 伤害数字弹出 |
| 回位 | 15-40% | 前顶回弹 |
| 待机 | 40-100% | 呼吸动画，攒下一次 |

**大招节拍**（总长 ~1.6s，含特写切镜）：

| 相位 | 时间 | 表现 |
|---|---|---|
| 蓄力抬手 | 0-0.3s | 精灵下蹲后仰 2px、底座能量环提亮加速循环、头顶蓄力光点 |
| 特写切镜 | 0.3-0.5s | §4.2.3：施法者大图 + 招式名横幅 |
| 特效播放 | 0.5-1.1s | battle_fx 属性 OAM 图元（35 张按 17 属性映射，复用 PokeWalk） |
| 判定与后摇 | 1.1-1.6s | 命中：三色伤害数字 + 目标受击白闪；未命中：目标侧移 2px 蹲避（金银「避开了」演出）；施法者 0.2s 硬直防连续切镜眩晕 |

**连续大招合并窗**：0.2s 内排队多个 cast 只切一次镜（防切镜连击）；
**能量满预告**：能量条满后底座环进入呼吸闪烁（观战者可预判下一发大招，
读战况用）；抬手态静态参考已上战斗稿（雷丘，见 battle_240x320.png）。

（7 列 × 34px）。v2 的教训留档：先把整场事件应用完再逐帧渲染，会让「未来阵亡」
的单位以负 age 落进死亡闪白分支（全程白色剪影）、血条/位置显示终局值。
这同时验证了两件事：§4.6 节拍表在真实事件流上可执行；渲染端只是事件流回放器
（宪法 2.6）——M4 的 C 内核渲染按同一路径实现。已知待办：招式名暂用英文原名

模式（见 §4.9），GIF 修复记录：GIF 保存禁用 optimize（帧合并不累加 duration
导致播放变快、观感发白闪烁），消息窗改深色底。
